## 本次改动与边界

已证实的问题是发送内容与板端命令回显不一致，且缺字的 FaceProbe 未成功执行；接收端、中断服务或串口传输中哪一层导致缺字，尚未定位。冻结与命令丢字是否同一根因，也尚未证实。

本次采用一个可回退的发送节奏对照：连接探测、Door 命令和 Face 命令统一逐字符发送，每个字符写入并 flush，字符之间等待 3 ms；一条命令完整发送期间互斥。波特率保持 115200。使用停止事件可打断等待，检查写入长度，避免把不完整写入当作成功。

配置项：`SMART_ACCESS_SERIAL_CHAR_INTERVAL`，单位秒，默认 `0.003`，允许范围 0～0.05。设置 `0` 可以恢复整行一次发送用于对照。它不是串口波特率，也不改变原 15 秒离线判定。不会自动重发开门授权。

日志新增 `char_interval_ms`，状态接口新增 `serial_char_interval_ms`。同时记录原来不认识的非空串口文字，过滤特征分块正文及长 Base64 内容。日志位置和轮转上限保持不变。

这是针对命令缺字的可回退调整，需要实板验证；不能声称已修复板端冻结。不修改固件，无需重烧。

## 用户执行步骤

1. 在原 PowerShell 后端窗口 Ctrl+C，等待退出。关闭占用 COM10 的 MobaXterm/K-Flash 串口会话。

3. 等待板端启动，直接启动下面的后端；后端握手会启动摄像头，无需再进 MobaXterm 执行 Face start。

```powershell
$env:SMART_ACCESS_BRIDGE_MODE='serial'

& ..\.venv\Scripts\python.exe -m app.main
```

4. 网页确认 COM10 真实串口上线、LCD 画面更新。保持与本次故障相同的无人场景，观察约 15 分钟，不切换串口或模式。
5. 成功上线后可以在另一 PowerShell 中检查参数：

```powershell
(Invoke-RestMethod 'http://127.0.0.1:8000/api/devices/status').serial_char_interval_ms
```

预期输出 `3`。若没有该字段或值不符，先确认运行的是此项目新启动的后端。

2026-10-15 补充：曾遗漏在 API 的 `BridgeStatusOut` 响应模型中声明此字段，导致参数已经生效，但接口仍将字段过滤，PowerShell 因而没有输出。现已补充声明。正在运行的后端需要下次重启后才能返回该字段；当前观察无需中断，可查看通信日志中的 `tx` / `tx_probe` 记录，`char_interval_ms: 3.0` 说明当前发送间隔已生效。

6. 若再冻结，不要立刻 Reset；保留日志并记录时间。在另一 PowerShell 读取最后 200 行，或直接提供整个日志文件路径：
